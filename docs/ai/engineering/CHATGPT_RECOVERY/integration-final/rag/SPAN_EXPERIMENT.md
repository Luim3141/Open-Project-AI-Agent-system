# Source-span experiment — DEV only

`source_spans.py` is a bounded research prototype. Each returned `raw` span is an exact substring of the input Unicode text, with start/end Python code-point offsets and SHA-256 of both raw span and exact input text encoded as UTF-8. Offsets are **not byte offsets**, and input text must be the actual authorized, version-checked logical source, not a separately normalized file. JSON escapes remain raw. Splitting is sentence-limited; an oversized sentence and an oversized or malformed JSON block are omitted instead of being silently cut. A valid JSON block with duplicate keys or depth above 64 is omitted. Nested fields under secret-like key names are excluded, including through arrays and escaped names.

This is not a secret scrubber. Plain text and permitted fields may still contain secrets or prompt injection; field filtering is not sufficient to make a source safe. Existing registry, authorization, source revision checks, secret treatment, model input isolation and exact citation validation are mandatory. Decoded JSON text, aliases, arbitrary paths and implicit claims are not automatically equivalent to raw source evidence. Do not deploy this module or use it as answerability logic.

`span_dev_coverage.py` verifies the frozen dev manifest, source copies, PM actor scope, snapshot SQLite source hashes/versions and literal offsets. It found 13/13 positive dev supporting literals inside at least one raw span. This is a retrospective extraction coverage check only: it has **not** measured retrieval ranking, answerability, access control on the live path or freshness after mutation. Documents from the holdout source split appeared in previous dev retrieval; no document-unseen claim is justified. Holdout questions and labels remain unopened.

`run_span_smoke.py` prepares synthetic English/Vietnamese pairs and runs `span_reranker_offline.py` using the pre-existing pinned model and isolated runtime, `--network none`, CPU1 and 768 MiB. Run it only after the n8n clone finishes to avoid resource contention. Even if related passages score above unrelated ones, relevance alone is not entailment or proof that a citation answers a question. `span_dev_prepare.py` prepares local BGE + isolated Qdrant DEV pairs, verifies scoped source metadata and SQLite chunk hashes, then limits inference to at most two literal spans per retrieved document. It writes corpus-derived pair content only to the private operator directory. Its heuristic secret check does not guarantee sanitization. Do not run it if source registry/scope or clone state is uncertain.

Synthetic smoke completed once with 4/4 related-versus-unrelated pair orderings, pair p95 0.041536 s, model cold-load 3.2407 s, container wall 11.261 s and cgroup peak 570,318,848 bytes (`span-synthetic-smoke.json`). Scheduling messages crossed: this short smoke overlapped startup of the n8n targeted clone. Both the clone agent and root were notified; model container has exited. These simple synthetic pairs are not the dev benchmark and do not demonstrate entailment, no-answer accuracy or production latency.

Review of literal terms after extraction showed only 10/13 positive supporting spans share at least one normalized content token with the dev query. The current DEV candidate selector uses lexical overlap only to order spans within already retrieved chunks; it may omit paraphrases and must be checked for support-span recall before interpreting model scores. The overlap diagnostic is retrospective and is not a tuned threshold or evidence of answerability. Preparation checks clone point count and each frozen point's exact payload/vector, restricts project/actor/role and validates chunk hash/source offsets. The current secret scan recognizes only certain common patterns, cannot guarantee all credentials were removed, and is not a production authorization or sanitization control.

Use `PYTHONPATH=<workspace>/openproject/ai` when running the local preparation script. The clone Qdrant must already have the frozen `frozen_dev` collection at `127.0.0.1:16341`; do not start or modify MAIN Qdrant for this experiment. `run_span_dev_score.py` first measures three dev queries as a runtime pilot and stops if any exceeds five seconds by the measured lower-bound method. Its CPU inference is offline and bounded; the complete dev remains relevance-only, unthresholded and not deployable.

The bounded DEV scorer was subsequently resumed with cold BGE separated: raw document Hit@5 was 11/13, the supporting literal appeared in the highest-ranked returned span for 9/13, and 19/20 negatives had at least one unthresholded candidate. The last number is a candidate-generation count, not a false-positive rate or a valid answerability decision. Warm p95 was 0.4107 s for the sum of separately measured embedding/Qdrant and scorer pair times; this excludes production IPC and concurrency. Cold BGE was 11.82 s; scorer load 3.01 s, CPU1 peak 570 MB (`span-dev-warm.json`).

Post-hoc, `span_dev8_prepare.py` reused exactly that verified BGE/Qdrant document pool and selected at most eight spans per authorized document using positional coverage and lexical diversity. Supporting literal was in the candidate pool for 13/13 positive cases (VN 6/6, EN 6/6, mixed 1/1), versus 9/13 (VN 4/6, EN 4/6, mixed 1/1) when restricted to the top two raw chunks and at most two spans per document. This expanded the scorer input from 142 to 1,301 pairs across 33 queries, at most 40 pairs/query. This is an ablation on already observed development cases, with correlated language pairs; it is not independent evaluation.

`span_dev8_score.py` completed all 1,301 scores, CPU1/768 MiB/network-none; 13/13 positive queries had the expected document in top five, but only 9/13 had their frozen supporting literal in the top-ranked span chosen for that document. All 20/20 negative queries had an unthresholded candidate; this is **not FPR**, since the experiment has no answerability or abstention decision. Warm p95 for separately measured embedding/Qdrant + selection + summed pair inference was **2.143 s as a lower bound**, excluding production IPC, concurrency, and a unified end-to-end timing. First cold query lower bound was 13.480 s, peak cgroup 570,961,920 bytes, total five container walls 105.395 s (`span-dev8-relevance.json`). Two previously successful supporting spans were displaced by other same-document spans; two review cases also selected non-supporting spans. A purely post-hoc diagnostic threshold that retains at most one of 20 negatives retains only 9/13 supporting literals; relevance scores do not establish entailment. No threshold has been adopted, and this candidate is not suitable for MAIN deployment.

`anchor_guard.py` is a separate post-hoc syntax heuristic. On a replay of one already-scored dev candidate it removed two returned negatives while retaining 8/13 positive hits, but this has no independent predictive value and can reject legitimate synonyms, casing and aliases. A token's absence does not prove a negative fact. The guard is not authorized for production or for claiming benchmark success.
